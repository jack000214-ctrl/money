# 판단 계약

## 목적

모델이 바뀌어도 같은 질문을 받고 같은 종류의 답을 남기기 위한 계약이다. 설명용
최종 권위는 이 문서가 아니라 `cio/decision.py`와
`schemas/cio-decision.schema.json`이다.

## 입력: `cio-context/1.0.0`

`python3.13 -m cio prepare`가 다음 입력을 받는다.

```bash
# 새 자금 — NEW_BUY · ADD
python3.13 -m cio prepare <asset_id> \
  --price <검토가격> \
  --amount <최대사용금액> \
  --amount-currency <KRW|USD> \
  --intent NEW_BUY \
  --verbatim "사용자가 실제로 한 말" \
  --claim "사용자가 사실이라고 말한 것"   # 반복 가능

# 보유분 — HOLD_REVIEW · TRIM_REVIEW · EXIT_REVIEW
python3.13 -m cio prepare <asset_id> \
  --price <검토가격> \
  --intent TRIM_REVIEW \
  --quantity <검토 매도수량>            # 또는 --target-quantity <목표 잔여수량>
```

`--intent`는 무엇을 묻고 있는지다. 신규매수와 분할매도 검토를 하나의 "이 가격에
살까"로 정규화하면 그 차이가 사라진다.

**두 갈래는 받는 입력부터 다르다.** 새 자금은 가격과 최대 투입예산을, 보유분은
최신 보유수량(원장)과 검토 수량을 받는다. 초판은 모든 intent에 `--amount`가
필수였고 `proposed_trade`가 언제나 추가매수 수량·현금차감·매수 후 비중을
계산했다. 그래서 이런 packet이 나왔다.

```text
intent:   TRIM_REVIEW
question: "이 가격과 금액으로 매수하면 …"
proposed_trade: 40,000,000원 → 803주, 매수 후 비중 27.76%
```

묻지 않은 질문에 답을 만들어 주면 모델은 그 답을 근거로 받아들인다. 지금은
`request.intent_family`가 `NEW_CAPITAL`이면 `proposed_trade.side = BUY`,
`EXISTING_POSITION`이면 `SELL`이고 매수 사다리(`add_ladder`)는 실리지 않는다.
한쪽 입력을 다른 갈래에 주면 `prepare`가 거부한다 — 검사되지 않는 우회로를
남기면 그 길로 간다. `REBALANCE`만 어느 입력을 줬는지로 갈래가 정해진다.

매수 예산이 실리지 않은 packet에서는 `proposed_trade.amount`를 0보다 크게 낼 수
없다. 사용자가 이번에 허락한 돈이 없다는 뜻이며, 종목 관점은 `thesis`에 남기고
새 자금 판단은 `NEW_BUY`·`ADD`로 다시 묻는다.

### 준비상태는 두 질문이다

`--held-quantity`와 선택적인 `--average-cost`는 보유분 검토에 한해 받는다.
`request.position_input`이 출처(`USER_INPUT`)·시점·통화·미확인 상태를 봉인하고,
`portfolio.scope = USER_SUPPLIED_POSITION`일 때 `existing_position`은 그 조건을
사용한다. 원장과의 차이는 `local_position_comparison`에 남긴다. 이 경우
`position_action: PASS`는 **명시된 조건 안에서 수량을 대조할 수 있다**는 뜻이며
실제 잔고 인증이 아니다. 원장 부재·낡음은 조건부 분석을 막지 않는다.

`--average-cost-currency KRW|USD`는 평단의 실제 표시 통화이며 생략하면 자산 통화다.
예를 들어 미국 주식 100주와 원화 평단 6,000원은 `--held-quantity 100
--average-cost 6000 --average-cost-currency KRW`로 보존한다. `request.position_input`
및 `existing_position.average_cost_currency`가 그 통화를 표시한다. 원장과 통화가
다르면 `average_cost_comparable=false`, `average_cost_matches=null`이다.

평가액은 날짜가 있는 환율로 환산할 수 있지만 **과거 취득원가는 현재 환율로 복원할
수 없다.** 원화 평단만 있으면 `cost_basis_krw`와 원화 손익을 계산하고 달러
`average_cost_asset_currency`·`cost_basis`·`unrealized_pnl`은 null이다. 달러 평단만
있으면 달러 원가·손익을 계산하고 실제 `cost_basis_krw`·`unrealized_pnl_krw`는 null이다.
`usd_pnl_at_current_fx_krw`는 달러 손익의 현재 환산액일 뿐 실제 원화 투자손익이 아니다.
`unrealized_pnl_pct`는 `unrealized_pnl_return_currency` 기준이며,
`break_even_price_at_current_fx`는 현재 환율이 유지된다는 조건의 자산 통화 가격이지
달러 취득평단이나 투자 가치평가가 아니다. 환율이 없거나 날짜가 없으면 필요한 환산
산술만 null로 두며 보유수량 대조 자체를 막지 않는다.

로컬 보유 스냅샷의 `(value_krw - pnl_krw) / quantity`도 원화 평단이다. 미국 자산이라고
현재 환율로 나누어 달러 취득평단으로 표시하지 않는다. 거래 원장의 달러 평단은
별도 경로이며 두 통화의 평단을 합치지 않는다.

원장·과거 거래·정책 파일은 바꾸지 않으며 원장의 실현손익을 시나리오에 붙이지 않는다.
총자산·현금·계좌 비중은 null이다. 추가 보유분의 매수 자금이나 매도 이력을 모르는데
계좌 분모를 추정하면 금액 제한 검사까지 잘못 통과하기 때문이다. 사용자 입력을
그 자체로 CONFIRMED 처리할 수 없고 독립 근거가 없으면 UNVERIFIABLE로 닫는다.
매도수량 상한과 EXIT 전량 검사는 기존처럼 이번 packet의 보유수량과 대조한다.

`validation.status`(=`readiness.security_view`)는 **종목 관점을 세울 수 있는가**이고
`readiness.position_action`은 **실제 수량 지시를 낼 수 있는가**다. 원장이 낡았으면
"이 종목은 비싸다"는 여전히 말할 수 있지만 "30주 중 10주를 팔아라"는 말할 수
없다 — 30주가 아직 30주인지 모르기 때문이다.

| position_action이 BLOCKED되는 조건 | 왜 |
|---|---|
| 원장이 없거나 읽을 수 없다 | 대조할 수량이 없다 |
| `portfolio:holdings`가 FRESH가 아니다 | 사용자가 갱신해야 하는 파일이다 |
| 보유는 있는데 수량이 없다 | 부등호 비교가 성립하지 않는다 |
| 매도 intent인데 원장에 보유가 없다 | 질문과 원장이 다르다 |
| 검토 수량이 보유수량을 넘는다 | 입력 자체가 성립하지 않는다 |

`BLOCKED`면 `action.direction`은 `UNDETERMINED`(`NO_POSITION_DATA`)여야 하고
verdict·가격계획은 그대로 낸다. 이 검사가 없을 때는 셋 다 `optional_gaps` 경고일
뿐이어서 낡은 원장 위에서 매도 수량이 그대로 저장됐다 — fail-open이었다.

로컬 재무보다 새 실적 공시가 있는데 **그 원문마저 로컬에 없으면** `security_view`가
BLOCKED된다. 색인에 제목이 있다는 것은 근거가 있다는 뜻이 아니다. 삼성전자 TTM
영업이익이 로컬 94.1조 vs 이미 공시된 179.0조로 1.9배 벌어진 채 경고 한 줄만 달고
통과한 적이 있다. 받는 방법은 problems 문장이 직접 알려준다.

`--verbatim`과 `--claim`은 **분석의 전제가 아니라 검증 대상으로** 실린다. 사용자는
이미 사고 싶은 상태에서 묻고("실적 1,860% 나왔더만"), 강한 모델일수록 그 프레이밍을
정교하게 보강한다. 그래서 원문은 넣되 `USER_ASSERTED` 라벨을 붙여 넣고, 각 주장은
판단에서 닫혀야 한다(아래 `user_assertion_checks`).

컨텍스트에는 다음만 포함한다.

- `request`: 자산, 가격·통화, 금액·통화, 기준시각, 질문, 의도, 사용자 원문과 주장
- `asset`: 시장, 상품 유형, 산업, 분석 렌즈, 방법론 후보, 벤치마크
- `validation`: PC가 확인한 준비 상태와 문제 목록
- `context`: 가격 요약, 벤치마크, 시장, 재무, 공시 색인(DART·SEC), 적용 가능 계산,
  이벤트, ETF 구조, 포트폴리오 영향, 사용자 투자정책, 최근 판단, 미해결 수집 요청,
  보존한 웹 원문
- `research_requirements`: 로컬 데이터 밖에서 모델이 확인할 질문
- `evidence_index`: 로컬 산출물의 ID, 경로와 기준시점
- `model_contract`: 공통 prompt와 decision schema 위치

전체 공시·뉴스·과거 대화를 넣지 않는다. 모델은 evidence index와 요약으로 시작하고,
결론을 바꿀 수 있는 빈칸만 추가 조사한다.

### 판단을 이어 붙이는 블록

한 종목을 여러 번 묻는 것이 이 시스템의 정상 사용법이므로, 컨텍스트는 직전
판단을 이어받을 수 있을 만큼만 함께 싣는다.

| 블록 | 내용 | 왜 |
|---|---|---|
| `prior_assessments[].carried_forward` | 직전 판단의 논지·가격계획·무효화 신호 | 모델이 자기 계획을 확인하고 시작하게 한다 |
| `prior_assessments[].price_vs_prior_plan` | 그 문턱과 현재 종가의 산술 대조 | 문턱 도달 여부는 PC가 계산한다 |
| `prior_assessments[].usable: false` | 현재 계약으로 재검증되지 않는 판단 | 계약이 바뀌었을 때 기억이 조용히 사라지지 않게 한다 |
| `open_research_requests` | 아직 처리되지 않은 모델의 수집 요청 | 요청이 편지함에서 썩지 않게 한다 |
| `local_documents` | 공시 원문과 보존한 웹 원문의 단일 목록(+미수집 공시 수) | 100만 자 문서를 넣지 않고 존재만 알린다. `url`이 있으면 모델이 이전에 보존한 웹 원문이며, 같은 조사를 반복하지 않게 한다 |
| `fundamentals.reporting_lag` | 로컬 재무 기준일 이후의 공시 | 신선도를 시계가 아니라 결산 캘린더로 잰다 |
| `fundamentals.earnings_bridge` | 최근 8분기 매출·매출총이익·영업이익·순이익·OCF·FCF와 YoY/QoQ·마진 | 수집기는 8분기를 저장하는데 packet은 TTM 네 숫자만 실었다. 압축은 삭제가 아니라 변환이다 |
| `data_coverage` | 입력별 가용성 — 있다 / 등록했는데 없다 / 등록 안 했다 / 이 시장에 수집기가 없다 | 빈칸은 "해당 없음"으로 읽힌다. 못 받는 것을 못 받는다고 말한다 |

### `earnings_bridge` — 이미 있는 것을 지우지 않는다

TTM 네 숫자만 실으면 분기 흐름이 packet에서 사라진다. 삼성전자 영업이익
4.68조 → 12.17조 → 20.07조 → 57.23조는 저장된 8분기만 봐도 보이는데, 그것을
확인하려고 DART 원문을 다시 뒤진 적이 있다 — **근거의 절반이 이미 로컬에
있었고 packet이 지웠다.**

표에 나오는 값은 전부 합·차·비율이다. 기준이 0 이하면 변화율을 비운다(적자에서
흑자로 가는 변화율은 해석 불가능한 수다). `derived`는 실측이 아니라 복원값이라는
표시이며(4분기 = 연간 − 3분기 누계), `metrics_absent`는 그 항목의 분기 시계열이
아예 없다는 뜻이다 — 0이 아니라 결측이다. **추세 판정은 이 표에 없다.**

기준일 이후에 나온 실적 공시는 `unreflected_result_disclosures`로 **숫자를 읽는
자리에** 붙는다. 경고를 `optional_gaps`에만 두면 다른 항목들 사이에 묻히고,
주의력에 의존하는 안전장치는 안전장치가 아니다. 공시는 이미 끝난 기간만 보고할
수 있으므로 로컬 기준일 다음 분기말 전에 나온 공시는 여기 세지 않는다 — 3월 말
재무에 5월 초 1분기 잠정실적을 미반영으로 세면 없는 공백이 매번 켜진다.

`carried_forward`의 주된 용도는 회고와 개선이다. 현재 근거로 판단한 뒤 과거와
대조하며, 과거 결론·가격선·가정은 언제든 버릴 수 있다. 새 사실이 없어도 기존
해석의 오류나 방법론 개선으로 바꿀 수 있다. 유지할 때도 현재 근거를 설명한다.
과거 기록의 보존과 과거 판단의 채택은 다른 문제다.

### `investor_policy` — 종목이 아니라 자본에 대한 제약

`context.investor_policy`는 `config/investor-policy.json`을 실어 보낸다. 모델은
"이 종목이 좋은가"를 판단할 수 있지만 "그래서 이 사람 돈 얼마를 쓰는가"는
사용자만 아는 한도 위에서만 답할 수 있다. 이 값들이 CSV 주석에만 있으면 어떤
모델도 읽지 못한다.

PC가 여기서 하는 일은 둘뿐이다 — 한도를 **그대로** 싣고, 한도와 현재·매수후
수치를 **산술로 대조**한다. `checks[].breach_now`는 부등호 비교의 결과이지
매도 지시가 아니며, 넘었을 때 무엇을 해야 하는지는 PC가 정하지 않는다.

| check | 방향 | 무엇과 대조하나 |
|---|---|---|
| `concentration.max_single_position_pct_of_total` | MAX | 검토 가격 기준 현재 비중 / 매수후 비중 |
| `concentration.max_sector_pct_of_total` | MAX | **대조하지 않는다** — ETF look-through가 없다 |
| `liquidity.min_cash_krw` | MIN | 현재 현금 / 매수후 현금 |
| `risk.max_loss_per_position_krw` | 환산 | 노출로 나눠 `PCT_OF_POSITION_VALUE`로 |

섹터 한도를 직접 보유만으로 계산하면 ETF 안의 같은 섹터 노출이 빠져 실제보다
작게 나온다. 틀린 여유를 주느니 `INPUT_UNAVAILABLE`로 답한다.

최대 손실 한도는 그 자체로 대조할 상대가 없어 노출로 나눈 환산값을 준다.
**손절가를 거기 두라는 뜻이 아니라**, 논지에서 나온 손절이 한도 안인지 밖인지
대조하라는 뜻이다.

**`unset`은 "제한 없음"이 아니라 "사용자가 아직 정하지 않음"이다.** 둘을 섞으면
한도 없는 상태를 무제한으로 읽고 수량을 마음대로 정하게 된다. 그래서 한도가
비어 있으면 `breach`를 `false`로 접지 않고 `null` + `LIMIT_UNSET`으로 남긴다.
PC는 비어 있는 한도를 그럴듯한 기본값으로 채우지 않는다 — 채우는 순간 그것은
사용자의 정책이 아니라 프로그램의 가정이고, 그 사실이 출력에서 사라진다.

```bash
python3.13 -m cio policy          # 정한 한도와 아직 정하지 않은 한도
```

정책 파일에는 최대 손실액·목표수익·계좌 유형이 들어가므로 `holdings.csv`와 같이
`.gitignore` 대상이다. 구조는 `config/templates/investor-policy.json`으로 버전
관리하고, **판단 시점의 실제 정책은 매 `prepare`마다 `POLICY:INVESTOR` source로
`knowledge/evidence/`에 내용 지문으로 봉인**되므로 재현성은 잃지 않는다.

packet이 예산(`MAX_CONTEXT_JSON_BYTES`)을 넘으면 서술부터 버리고 가격 문턱과
무효화 신호를 남긴다. 버린 항목은 `validation.optional_gaps`에
`TRIMMED_FOR_BUDGET`으로 기록되며, 원문은 `knowledge/assessments/`에 그대로 있다.

## 출력: `cio-decision/1.0.0`

모델은 Markdown 설명을 섞지 않고 JSON 객체 하나를 반환한다. 필수 결론은 다음과
같다.

| 영역 | 필수 내용 |
|---|---|
| 판단 | `verdict`, 측정 metric, 기간, 승리·실패 정의와 각각의 수익률 문턱 |
| 확률 | 승리 확률, 분석 신뢰도, 약세·기준·강세 확률 |
| 기대수익 | 약세·기준·강세 및 확률가중 수익률 |
| 가격 계획 | 선호 진입가·범위, 손절가, 분할매도 시작가, 재질문 하단·상단·사건 |
| 금액 | 사용자가 제시한 한도 안의 제안 금액과 이유 |
| 보유분 행동 | `action`의 방향·수량·매도 사유와 이유 |
| 논지 | 핵심 논지, 가장 강한 반대 논지, 관측 가능한 무효화 신호 |
| 조사 배분 | `drivers` — 이익 동인과 비중, 각 동인을 조사했는지 건너뛰었는지 |
| 근거 | 방법론·가정, 모르는 것, 추가 조사 요청, 출처와 evidence ID |
| 재현성 | context ID와 모델·prompt 버전 |

### `drivers` — 조사를 배분한다

결론 전에 이익 동인을 나열하고 **비중의 합이 100이 되도록 배분**한다. 각 동인은
조사했거나(`researched: true` + `finding`) 건너뛰었거나(`researched: false` +
`skipped_reason`) 둘 중 하나여야 하며, 둘 다이거나 둘 다 아닐 수 없다.

합을 100으로 강제하는 것이 이 계약의 요점이다. **"다 중요하다"는 배분이 아니다.**
동인이 여럿인 회사에서 순서를 정하지 않으면 이익에 거의 영향이 없는 이야기에
판단의 무게가 실린다 — 어떤 사업부가 영업이익의 5%인지 50%인지 모른 채 그
사업부의 최신 뉴스부터 읽는 것이 그 실패다.

`basis`는 그 비중의 근거다. 부문별 매출과 비중은 사업보고서에 있으므로
`cio search`로 확인해 쓴다.

건너뛰는 것은 정당하다. 모든 동인을 매번 조사할 수는 없다. 다만 건너뛴 사실과
이유가 다음 컨텍스트의 `carried_forward.drivers`로 넘어가므로, 같은 동인을 계속
미루고 있으면 그것이 드러난다.

### `positioning` — 이익 동인이 아닌 가격 결정 요인

`drivers`는 **이익** 동인만 100%로 배분한다. 그래서 수급·포지셔닝은 그 표에 칸이
없고, packet에 실려 있어도 판단의 무게에서 조용히 빠진다.

실제로 그 실패가 있었다. 2026-07-29 삼성전자에서 기관이 597만주를 순매수하고
거래량이 평소의 2.5배였는데(`structured_optional.kr_flow`로 packet에 실려 나갔다)
다음 판단의 논지는 판가 얘기만 했다. 이틀 뒤 +20%였다.

**`structured_optional.kr_flow` 또는 `kr_lending`이 packet에 있으면 `positioning`은
필수다.** `drivers`와 같은 규율을 쓴다 — `checked: true` + `finding` 이거나
`checked: false` + `skipped_reason`이며, 둘 다이거나 둘 다 아닐 수 없다.

`unobservable`에는 보고 싶었으나 없던 것을 적는다. 여기 쌓이는 항목이 다음 수집기의
우선순위가 된다. 실제로 그렇게 굴러갔다 — 두 판단이 여기에 적어 둔 세 항목을 2026-08-03에
찾아 나섰고 하나만 받을 수 있었다.

| 항목 | 상태 |
|---|---|
| 대차잔고 | `KR_LENDING` 수집기로 들어온다 (`structured_optional.kr_lending`) |
| 공매도 잔고 | **구조적으로 없다.** 종목 단위 공개 경로가 존재하지 않는다 |
| 신용융자 잔고 | **종목 단위로 없다.** 시장 전체 추이만 공개된다 |

뒤의 둘은 "아직 안 만든 것"이 아니라 **받을 수 없는 것**이다. 그래서 packet의
`kr_lending._unobservable`이 매번 그 사실을 실어 보낸다 — 모델이 매 판단마다 같은
검색을 반복하지 않게 하기 위해서다. 근거는 [data-policy.md](data-policy.md#공매도-잔고를-받을-수-없는-이유)에 있다.

**대차잔고를 공매도 잔고로 읽으면 안 된다.** 대차는 공매도의 재료이지 공매도가
아니며, 결제·차익거래·의결권 목적의 대차도 같은 숫자에 섞여 있다. 잔고가 늘었다는
사실은 누가 왜 빌렸는지를 말하지 않는다.

맞히라는 것이 아니라 보고도 안 본 척하지 말라는 것이다. 동시에 수급은 이익 동인이
아니므로 `drivers`의 100%에 억지로 끼워 넣지 않는다.

### `user_assertion_checks` — 사용자 주장을 닫는다

packet의 `request.user_assertions`에 있는 각 주장은 판단에서 **확인·반박·확인불가**
중 하나로 닫혀야 한다. 하나라도 열려 있으면 판단을 저장할 수 없다.

| status | 필요한 것 |
|---|---|
| `CONFIRMED` | `claim_kind` + `basis` + `finding` + `evidence_refs` |
| `REFUTED` | 같음 |
| `UNVERIFIABLE` | `claim_kind` + `finding` (`basis`·근거 불필요) |

근거 없이 "확인했다"고 말하는 것은 확인이 아니므로 `CONFIRMED`·`REFUTED`에
`evidence_refs`를 요구한다. packet에 없는 `claim_id`를 지어내는 것도 거부한다.

#### 근거는 개수가 아니라 결속이다

초판은 `evidence_refs`가 비어 있지 않은지만 봤다. 그래서 **"영업이익 1,860%"를
가격 CSV(`PRICE:TSLA`)로 CONFIRMED** 하는 것과 **존재하지 않는 ID로 CONFIRMED**
하는 것이 둘 다 통과했다. 형식은 통과하고 의미는 검증되지 않는 자리였다.

- `claim_kind`가 무엇에 관한 주장인지 말하고, PC가 근거의 갈래와 대조한다
- `basis`의 `metric`·`period`·`comparison`이 무엇을 어느 기간에 무엇과 비교했는지
  말한다. 기저가 거의 0이면 1,860%는 성장이 아니라 나눗셈인데, 그 구분은 이
  세 칸을 채우지 않으면 사라진다
- `evidence_refs`의 ID는 `evidence_index`에 있거나 모델이 `sources`에 등록한
  것이어야 한다

| `claim_kind` | 닫을 수 있는 자료 |
|---|---|
| `PRICE` | 가격 시계열, 계산 |
| `EARNINGS` | 재무 스냅샷, 보존한 공시 원문, 계산 |
| `VALUATION` | 위 둘 + 컨센서스 |
| `OWNERSHIP` | 수급·대차 |
| `BUSINESS` | 보존한 원문, 모델이 조사한 출처 |
| `MARKET` | 시장 국면, 가격, 조사한 출처 |
| `EVENT_DATE` | 공시 색인·캘린더, 원문 |
| `PORTFOLIO` | 보유·정책·거래원장 |

**이 대조는 투자 판정이 아니다.** 가격 CSV에 영업이익이 없다는 것은 파일을 열어
보면 아는 사실이고, 공시 색인에 제목만 있다는 것도 마찬가지다. 무엇이 확인이고
무엇이 반박인지는 여전히 전부 모델이 정한다.

`REFUTED`는 실패가 아니라 이 시스템이 존재하는 이유에 가깝다.

### `research_requests` — 편지함이 아니라 대기열

모델이 "로컬에 이것이 필요하다"고 적는 필수 필드다. 이 요청은 assessment 안에서
끝나지 않는다.

```bash
python3.13 -m cio requests <asset_id>                    # 미해결·해결 목록
python3.13 -m cio requests <asset_id> \
  --resolve REQ-3e547a42822d --state DONE --note "무엇을 했는지"
```

요청의 신원은 정규화한 본문의 sha256이다. 같은 요청을 여러 판단에서 반복하면
`asked_count`가 올라가고, 그 횟수가 우선순위 신호가 된다. 미해결 요청은 다음
컨텍스트의 `open_research_requests`로 되돌아온다.

**같은 뜻의 요청은 문장이 달라도 한 묶음이 된다.** 모델은 매 판단에서 같은
요청을 조금씩 다르게 쓴다 — 마침표 하나, `재수집해`와 `재수집하고`. 본문 해시만
쓰면 목록이 사실상 같은 말로 채워지고 `asked_count`가 언제나 1이 되어 반복
신호가 죽는다. 그래서 구두점과 공백을 버린 표기의 유사도가 0.62 이상이면 묶는다.
실제 데이터에서 같은 뜻의 요청은 0.69 이상, 서로 다른 요청은 0.45 미만에 몰려
그 사이가 비어 있다.

30자 미만은 유사도를 쓰지 않고 정확히 같을 때만 묶는다. 짧은 문자열은 유사도가
부풀려져 `요청 0`과 `요청 1`이 0.8로 나오기 때문이다.

묶음의 대표는 **가장 먼저 요청된 문장**이라 나중에 비슷한 요청이 들어와도 ID가
바뀌지 않는다. 해결은 대표에 걸리며 묶음 안 어느 문장으로도 닫을 수 있고, 한 번
닫으면 나중의 재표현도 미해결로 돌아오지 않는다. 묶인 문장은 목록에 `↔`로 함께
보여, 잘못 묶였으면 눈에 띄게 한다.

**해결 판정은 사용자만 한다.** 모델이 자기 요청을 닫을 수 있으면 "요청했는데
아직 없다"는 신호가 의미를 잃기 때문이다. `state`는 `DONE`(만들었다),
`DECLINED`(만들지 않기로 했다), `SUPERSEDED`(다른 것으로 대체됐다)다.

### 근거 보존과 검색

모델이 조사한 원문은 인용 전에 로컬에 남긴다.

```bash
python3.13 -m cio snapshot <URL> --asset <asset_id> --label <이름> --note "왜"
python3.13 -m collectors.dart document <14자리 접수번호>
```

보존한 원문은 검색해서 필요한 자리만 쓴다.

```bash
python3.13 -m cio docs <asset_id>
python3.13 -m cio search <asset_id> <검색어> [--context N] [--limit N] [--fixed]
```

부문별 매출·주요 매출처·수주잔고·생산능력처럼 **회사 구조에 관한 사실은 웹보다
로컬 원문이 먼저다.** 부문 비중을 모른 채 특정 사업부의 최신 뉴스부터 읽으면
이익에 거의 영향이 없는 이야기에 판단의 무게를 싣게 된다.

`snapshot`은 받은 바이트를 그대로 내용 지문으로 저장한다. 광고나 마크업을
걷어내지 않는다 — 페이지 구조는 언제든 바뀌지만 저장한 바이트는 바뀌지 않고,
무엇이 본문인지는 그 파일을 읽는 모델이 판단한다. 응답이 프레임 껍데기면
`shell_page_warning`이 붙으며 그 스냅샷은 내용 근거가 아니다.

### Verdict

- `BUY_NOW`: 제시 가격에서 매수를 선호한다. 기존 보유가 있어도 추가 매수는 이
  verdict로 표현한다.
- `WAIT`: 자산은 검토 가치가 있지만 더 나은 가격 또는 사건을 기다린다.
- `AVOID`: 현재 논지·가격·위험 조합을 피한다.
- `INSUFFICIENT`: 조사 후에도 책임 있는 숫자 판단을 만들 정보가 부족하다.

`INSUFFICIENT`는 쉬운 탈출구가 아니다. 로컬 구조화 데이터 갱신과 모델의 직접
조사 후에도 결론을 지탱할 수 없을 때만 사용한다. 이때 `action.direction`은
`UNDETERMINED`여야 한다 — 자세한 이유는 아래 Action 절에 있다.

### Action — 가진 것을 어떻게 할 것인가

`verdict`는 **새 자금**에 대한 판단이고 `action`은 **이미 보유한 수량**에 대한
판단이다. 두 질문은 다르며 동시에 참일 수 있다. 더 사지 않지만 팔 이유도 없으면
`WAIT` + `HOLD`다.

`direction`은 `ADD | HOLD | TRIM | EXIT | UNDETERMINED`이며 매도(`TRIM`·`EXIT`)에는
수량과 `sell_reason`이 필요하다.

#### `HOLD`는 빈 값이 아니다

보유 중인 종목에서 `HOLD`는 "이 수량을 이 가격에 계속 들고 있어라"는 적극적
지시다. 그래서 판단이 서지 않을 때 `HOLD`를 쓸 수 없다 — 쓰는 순간 시스템이
모델의 **"모른다"를 "보유하라"로 번역**한다.

정할 수 없으면 `UNDETERMINED`이며 `undetermined_reason`으로 무엇이 없어서
정할 수 없는지 밝힌다. 이 값은 선택 필드다(계약을 조일 때마다 과거 판단이
끊기는 것을 막기 위해 `recurring_plan`과 같은 규칙을 따른다).

| 사유 | 언제 | 푸는 사람 |
|---|---|---|
| `INSUFFICIENT_EVIDENCE` | 조사 후에도 종목 판단 자체가 서지 않는다 | 수집기·조사 |
| `NO_INVESTOR_POLICY` | 종목 관점은 섰으나 한도가 없어 수량을 못 정한다 | 사용자 |
| `NO_POSITION_DATA` | 보유 상태·평단을 신뢰할 수 없다 | 로컬 데이터 |
| `USER_INPUT_REQUIRED` | 적립 가동 여부처럼 사용자만 아는 사실이 필요하다 | 사용자 |

`verdict: INSUFFICIENT`와 `undetermined_reason: INSUFFICIENT_EVIDENCE`는 같은
사실의 두 면이라 항상 함께 간다. 나머지 셋은 일반 verdict와 함께 쓴다. 이
구분이 있어야 "데이터가 없어 막힌 비율"과 "정책이 없어 막힌 비율"이 따로
집계된다 — 둘은 해결할 사람이 다르므로 한 통에 넣으면 무엇을 고쳐야 하는지
알 수 없다.

`UNDETERMINED`는 수량·매도사유를 가질 수 없고 새 집행액도 가질 수 없다.
행동을 정할 수 없다면서 돈을 넣을 수는 없기 때문이다.

**아직 이 계약이 표현하지 못하는 것.** "종목은 매력적인데 한도가 없어 얼마를
살지 못 정하겠다"를 `BUY_NOW`로 낼 수 없다 — `BUY_NOW`는 0보다 큰 집행액을
요구하기 때문이다. 현재는 `WAIT` + `UNDETERMINED`(`NO_INVESTOR_POLICY`)로 내고
종목 관점은 `thesis`에 남긴다. 이 한계가 `verdict`가 아직 "매력적인가"와
"얼마를 넣는가"를 한 필드에 묶고 있다는 뜻이며, 종목 관점과 포트폴리오 행동을
분리하면 사라진다.

`sell_reason`은 두 갈래로 나뉘고, 이 구분이 사후 평가의 집계 단위가 된다.

| 갈래 | 사유 | 규칙 |
|---|---|---|
| 판단 기반 | `THESIS_BROKEN`, `VALUATION`, `BETTER_OPPORTUNITY` | 자산 자체에 대한 판정이라 `BUY_NOW`와 함께 쓸 수 없다 |
| 제약 기반 | `CONCENTRATION`, `RISK_BUDGET`, `LIQUIDITY_NEED` | 자산이 좋아도 낼 수 있으나 제약임을 밝혀야 한다 |

**밸류에이션과 논지가 매도를 주도한다.** 비중·변동성·시장 국면은 노출 측정치이지
그 자체로 매도 사유가 아니다. 사용자가 명시한 한도가 없는 한 비중을 이유로 매도를
권하지 않으며, 노출은 숫자로 보여주고 판단은 사용자에게 맡긴다. 제약 때문에 파는
것이 옳더라도 그것을 밸류에이션 판정처럼 포장하지 않는다.

### 수량은 원장과 대조된다

`action.direction`과 `action.quantity`는 packet의 `portfolio.existing_position`과
기계적으로 비교된다.

```text
TRIM            보유 중 AND 0 < quantity < 보유수량
EXIT            보유 중 AND quantity == 보유수량
HOLD            보유 중 AND quantity == null
ADD             quantity == null
NOT_APPLICABLE  미보유 AND quantity == null
```

초판은 매도 수량이 양수인지만 봤고, 그래서 95주 보유 중 `TRIM` 999주, 95주 보유 중
`EXIT` 1주, 미보유 종목에 `TRIM`·`EXIT`·`HOLD`가 전부 통과했다. 매도는 되돌릴 수
없는 행동이며 이 검사는 종목의 좋고 나쁨에 대한 판정이 아니라 **보유 수량과 지시
수량의 부등호 비교**다. 얼마나 팔지는 여전히 전부 모델이 정한다.

`EXIT`은 전량이라는 뜻이다. 일부만 팔면서 `EXIT`을 쓰면 수량이 아니라 **상태**가
틀린다 — 다음 판단의 packet이 이 종목을 정리된 것으로 읽는다. 정수주는 강제하지
않는다. 이 사용자의 원장에는 소수 수량(TSLA 10.004156주)이 실재한다.

원장이 없거나 수량을 모르면 대조하지 않는다. 없는 값을 지어내 막으면 그것은 검사가
아니라 가정이다. `tests/test_sell_quantity_contract.py`가 이 경계를 고정한다.

### 지시에는 실행 가격이 붙는다

`action.limit_price`는 **지금 증권사에 넣을 지정가**다.

```text
TRIM · EXIT      필수
ADD              선택 (진입가는 이미 price_plan.preferred_entry에 있다)
그 외            null
```

`price_plan.scale_out_start`가 이 자리를 대신하지 못한다. 그쪽은 "논지가 앞서가면
줄이기 시작할 가격"이라는 **미래 조건**이고 이쪽은 **지금 내는 주문**이다.

실제로 그 구분이 없어서 계획이 실행되지 못했다. 2026-08-07 11:16 판단은
`TRIM` 30주에 `scale_out_start` 470,000원이었고, 정작 실행가 "390,000원 이상"은
`action.rationale` 문단 안에만 있었다. 화면은 470,000원을 보여 줬고 수량 30주는
아예 렌더링되지 않았다. 그날 실적 발표는 몇 분 만에 주가를 15% 움직였으며 문단
안의 가격은 지정가로 걸리지 못했다 — 계획이 틀려서가 아니라 실행 가능한 형태가
아니어서다.

그래서 수량과 실행 가격은 `cio show` 화면의 결론 블록에 함께 찍힌다. 계약에만
있고 화면에 없으면 같은 일이 반복된다. `tests/test_execution_price.py`가 이
경계를 고정한다.

`limit_price`를 `required`에 넣지 않은 것은 의도다 — 필수로 만들면 이 필드가 없는
기존 판단이 전부 계약 미달로 끊긴다. 방향이 매도일 때만 검증이 요구한다.

## 승리와 실패

확률에는 측정 가능한 사건이 필요하다. 모델은 매 판단마다 다음을 명시한다.

- `horizon_months`: 평가 기간
- `win_definition`과 `win_return_threshold_pct`
- `failure_definition`과 `failure_return_threshold_pct`
- `win_probability_pct`: 위 승리 정의가 관측될 확률

**모든 수익률은 평가 기간 말의 누적이다** — `outcome_metric`이
`TERMINAL_TOTAL_RETURN_ASSET_CURRENCY`이므로 `expected_return_pct`도 문턱도 연율이
아니다. `reverse_dcf`는 시나리오마다 `total_return_pct`(누적)와
`annualized_return_pct`(연율)를 함께 내며 계약으로 가는 값은 앞엣것이다. 예전 출력의
`return_pct`는 연율이었는데 이름이 단위를 말해 주지 않아 24개월 누적 +44.4%가
+20.2%로 들어가는 오배선을 만들 수 있었다. 계산은 맞고 배선만 틀린 종류라 눈에 띄지
않는다. PC는 판단이 인용한 계산과 대조해 **연율 칸을 누적 칸에 옮겨 적은 경우**만
잡는다 — 앵커나 확률을 다시 잡아 계산기와 다른 값을 쓰는 것은 판단이며 막지 않는다.

`outcome_metric`은 v1에서
`TERMINAL_TOTAL_RETURN_ASSET_CURRENCY`로 고정한다. 즉 승리·실패는 입력 가격
기준 평가기간 말의 자산 통화 총수익률이며, 조정종가로 분배를 반영하되 환율·세금·
수수료·슬리피지는 제외한다. 자유문장 정의가 이 측정 기준을 다른 사건으로 바꿀 수
없다. 승리 문턱은 실패 문턱보다 커야 한다.

## 시나리오와 산술

- 약세·기준·강세 확률은 모두 0보다 크고 합이 100이어야 한다.
- 수익률은 `bear <= base <= bull`이어야 한다.
- `probability_weighted`는 세 수익률과 확률의 가중합이어야 한다.
- 일반 verdict에서는 확률과 수익률을 비워둘 수 없다.
- `INSUFFICIENT`에서는 확률·기대수익·가격 계획·제안 금액을 모두 `null`로 둔다.

PC는 이 관계를 검증할 뿐 시나리오와 확률을 대신 선택하지 않는다.

## 가격 계획

신규 매수 관점의 기계적 관계는 다음과 같다.

```text
stop_price < entry_range_low
entry_range_low <= preferred_entry <= entry_range_high
entry_range_high < scale_out_start
reask_below < 사용자가 제시한 가격 < reask_above
```

손절가는 단순 변동성 숫자가 아니라 `invalidation_signals`와 연결해 설명한다.
분할매도 시작가는 전량 매도 목표가가 아니다. 재질문 사건에는 실적, 공시, 임상,
ETF 구성·분배 정책 등 가격 외 판단 변경 조건도 포함한다.

**가격 문턱은 시간을 보지 않는다.** 같은 `scale_out_start`라도 두 달 만에 닿는 것과
24개월 만에 닿는 것은 다른 사건인데 문턱만으로는 구분되지 않는다. PC는 이 공백을
`prior_assessments[].pace_since_decision`으로 메운다 — 직전 판단 이후의 실현 수익,
평가 기간의 경과 비율, 승리 문턱까지의 진도, 그리고 사용자가 정한 연 목표수익률이
같은 기간에 냈을 값과의 배수다. 자산 통화와 투자자 정책의 기본통화가 같을 때만
배수를 계산한다. 다르면 기준일별 환율로 환산한 수익률이 없는 한 배수는 `null`로 둔다.
연율 환산은 쓰지 않는다. 2거래일 +10%를 연율화하면
천문학적 숫자가 나와 아무 의미가 없다. **이 값들은 문턱이 아니라 관측이며, 몇 배부터
무엇을 하라는 규칙을 PC는 갖고 있지 않다.**

## 무효화 신호와 사전 약속

`invalidation_signals`의 각 항목은 `{signal, action, rationale}`이다. `action`은
`EXIT`(전량 매도) / `TRIM_HALF`(절반 축소) / `REASK`(다시 묻는다)이며, 신호가 켜지면
보유분에 무엇을 할지 **미리** 정해 둔 계획이다. 모델은 현재 판단에서 언제든
수정·폐기할 수 있다. `override_reason`은 그 이유를 보존하는 기록이며 승인이 아니다.

행동을 사후에 정하면 늦는 이유는 구조적이다. 신호가 켜지는 날은 가격이 이미 무너진
날이고, 그날 다시 돌린 역산은 낮아진 가격에서 시작하므로 "더 싸졌다"가 기계적으로
도출된다. 손절가 10,000원짜리 판단이 정작 10,000원에서 20,000원부터 분할매도하라는
답으로 바뀌는 경로가 여기다.

PC가 검사하는 것은 두 가지뿐이며 둘 다 부등호 비교다.

| 검사 | 언제 | 무엇을 |
|---|---|---|
| 매도 규율 존재 | `risk.stop_style`이 `THESIS`일 때 | 최소 1개 신호의 `action`이 `EXIT` 또는 `TRIM_HALF`인가 |
| 약속 정산 | packet이 직전 신호를 실어 보냈을 때 | 전부 닫았는가, 약속과 다르게 행동하면 `override_reason`이 있는가 |
| 정산 결속 | 같음 | `signal_index`·`signal`·`committed_action`이 packet이 실어 보낸 값과 같은가 |

마지막 줄이 없으면 앞의 두 줄은 장식이다. 초판 검증기는 모델이 **쓴 값**만 보고
packet이 **실어 보낸 값**과 대조하지 않았고, 그래서 세 가지가 통과했다 — 전혀 다른
문장 두 줄로 정산하기, 같은 신호를 두 번 적어 개수만 맞추기, 그리고 직전 약속이
`EXIT`인데 `committed_action`을 `REASK`로 낮춰 적기. 마지막 것은 **미래의 판단이 과거의
약속을 다시 쓸 수 있다**는 뜻이고, 그러면 사전 약속이라는 장치가 통째로 무의미해진다.
막으려던 실패(손절가 10,000원짜리 판단이 정작 10,000원에서 20,000원부터 분할매도)를
내면서 "직전 약속은 원래 REASK였다"고 적으면 그만이기 때문이다.
`tests/test_prior_commitment_forgery.py`가 이 세 경로를 고정한다.

**어느 신호에 어느 행동을 걸지, 문턱을 얼마로 할지는 전부 모델이 정한다.** 앞의
검사는 사용자가 `THESIS`로 정해 가격 손절을 버렸는데 매도가 나올 자리마저 없는
상태를 잡는 것이고, 뒤의 검사는 약속을 뒤집을 때 사유를 남기게 하는 것이다. 뒤집는
것 자체는 막지 않는다. 새 사실뿐 아니라 기존 해석의 오류, 더 나은 방법론,
기대수익을 바꾸는 가격 변화도 이유가 될 수 있다. 과거의 `committed_action`을
다르게 적는 것만 막으며, 현재 판단은 모델이 다시 정한다.

`prior_signal_checks`는 packet이 직전 신호를 실어 보냈을 때만 필수다. 예산 압축이
신호를 버렸으면 닫을 대상이 없으므로 요구하지 않는다. 계약이 packet 예산에 종속되면
컨텍스트가 길어졌다는 이유로 판단이 저장되지 않는다.

제안 금액은 사용자가 제시한 금액을 넘을 수 없고 입력 금액 통화와 같아야 한다.
`BUY_NOW`는 0보다 큰 현재 집행액, `WAIT`와 `AVOID`는 0, `INSUFFICIENT`는 null이다.

조건부 분할매수는 선택 필드 `entry_plan`에 기록한다. 현재 제안액을 제외한 미래
배분을 저장된 요청 예산과 대조하고, 조건·취소 사유·유효기간·권리 단위를 보존한다.
`show`가 같은 계산을 표시하고 다음 packet으로 이어진다. 과거 조건 확인은
`entry_plan_checks`로 근거와 함께 기록하며 실제 주문·체결 관리를 하지 않는다.
[계약과 지원 범위](advisory-plans.md), [발견 당시 적대 검증](reviews/2026-09-08-290650-adversarial.md).

미래 분할매도는 별도 선택 필드 `exit_plan`에 둔다. 지금의 매도는 `action`에 남기고,
미래 단계의 수량 합은 packet 보유량에서 지금 매도 수량을 뺀 범위 안에서 검사한다.
단계별 자산통화 지정가·선행 단계·조건·취소 사유·유효기간을 보존한다. 후속 판단의
`exit_plan_checks`는 원래 단계와 근거에 결속되며, 가격 접촉이나 조건 확인을
실제 체결로 승격하지 않는다. [상세 계약](advisory-plans.md#미래-분할매도-계획).

## 방법론 분기

`asset.analysis_lens`와 `valuation_family`는 후보이며 모델이 적합성을 다시 판단한다.

- 일반 주식: 현금창출, 경쟁우위, 재무안전, 상대·절대가치
- 반도체 등 사이클주: 정상화 이익, 재고·가격·공급·capex와 사이클 위치
- 임상·적자 바이오: 현금 런웨이, 희석, 파이프라인 단계와 확률가중 가치
- 광역 ETF: 지수 방법론, 구성, 보수, 추적오차, 밸류에이션과 대안
- 파생 ETF: 기초자산, 옵션 구조, 상승 제한, NAV 침식과 분배 원천

하나의 DCF를 모든 자산에 강제하지 않는다. 선택한 방법과 적합한 이유, 중요한
가정을 `method`에 남긴다.

## 근거와 출처

`evidence_refs`와 가장 강한 반대 논지의 근거는 다음 중 하나를 가리켜야 한다.

- context의 `evidence_index`에 있는 로컬 source ID
- 모델이 직접 조사해 `sources`에 등록한 source ID

모델 조사 source는 식별자, 유형, 위치, 공개시각과 회수시각을 갖는다. 출처 없는
핵심 숫자와 반대 논지는 공식 판단으로 저장하지 않는다. 모델 source ID는 로컬
evidence ID를 재정의할 수 없고 `published_at <= retrieved_at <= decision.created_at`
순서를 지켜야 한다.

**출처의 갈래는 ID가 아니라 그 ID가 가리키는 것이 정한다.** 모델이 지은 ID는
주장일 뿐이다. 예전에는 접두사만 봐서 뉴스 기사에 `FUNDAMENTALS:…`라는 이름을
붙이면 재무 자료로 분류돼 실적 주장을 `CONFIRMED`로 닫을 수 있었다.

- 로컬 근거의 접두사(`FUNDAMENTALS:`, `PRICE:`, `KR_*:`, `FILINGS:` 등)는 모델
  source에 쓸 수 없다. packet의 `evidence_index`에 있는 ID를 그대로 인용한다.
- `DARTDOC:`·`WEBSNAP:`은 모델이 등록할 수 있지만, 그 원문이 로컬에 실제로
  보존돼 있을 때만 1차 원문(`PRIMARY_DOCUMENT`)이다. 보존하지 않은 ID는 직접
  조사한 출처(`MODEL_RESEARCH`)와 같다 — 인용 전에 `cio snapshot`이나
  `collectors.dart document`로 받는다.
- `CALC-`는 이 자산의 저장된 계산을 가리킬 때만 계산이다.

#### 보존 원문은 주소·본문·지문·시각이 한 문서여야 한다

ID가 색인에 있는지만 보던 때에는 넷이 따로 놀았다. 실제 저장 판단 8건의 보존
출처 87개를 전부 다른 주소로 바꿔도 통과했고, 본문이 지문과 맞지 않는 파일도
이름만 맞으면 1차 원문이었다. **파일이 있다는 것은 그 주소의 그 본문을 인용했다는
뜻이 아니다.** `DARTDOC:`·`WEBSNAP:` 출처는 다음을 전부 지켜야 1차 원문이다.

| 묶는 것 | 검사 |
|---|---|
| 본문 ↔ 지문 | 객체를 다시 지문 내어 파일 이름과 대조한다. 색인 캐시를 믿지 않는다 |
| ID ↔ 본문 | 웹 원문은 지문 앞 12자리, 공시 원문은 본문의 접수번호가 ID와 같다 |
| 주소 ↔ 본문 | 웹 원문의 `locator`는 그 본문을 받아 온 주소(요청 주소 또는 최종 주소)다. 공시 원문은 같은 접수번호의 DART 주소(`…/dsaf001/main.do?rcpNo=<접수번호>`)다 |
| 시각 | 판단 시각보다 늦게 보존된 원문은 그 판단의 근거일 수 없다 |
| 내용 | 프레임 껍데기(`shell_page_warning`)는 인용은 남지만 1차 원문이 아니다 |

앞의 넷을 어기면 계약 오류이고 그 출처는 `MODEL_RESEARCH`로 내려간다. 보존하지
않은 ID는 오류가 아니다 — 직접 조사한 출처일 뿐이다. 주소는 조각(`#…`)과 호스트의
대소문자만 무시하고 견준다. 같은 접수번호로 내용이 다른 객체가 둘 생기면 판단은
어느 쪽을 봤는지 고정하지 못한다(웹 원문은 ID가 내용 주소라 해당 없음). 지금
저장소에는 그런 접수번호가 없다.

로컬 근거도 시각 순서를 지킨다. `evidence_index`의 `data_as_of`가 context 생성일보다
뒤면 context 무결성 검사가 거부한다. 그때 없던 자료로 그때의 판단을 뒷받침할 수
없다. 사용자 원장(`USER_DATA`)은 예외다 — 그 기준일은 수집한 관측이 아니라
사용자가 적은 거래의 날짜(결제일)라 며칠 뒤일 수 있다.

모델이 직접 조사한 `sources`는 URL과 시각을 보존하는 **citation metadata**다.
프로그램은 URL 형식과 시각 순서를 검사하지만 페이지의 실재·당시 내용까지
보존했다고 주장하지 않는다. 정확한 본문 재현이 필요한 결정 핵심 자료는 전용
수집기로 로컬 evidence를 만든 뒤 새 context에 포함해야 한다.

## 검증과 저장

### 판단의 질에 남아 있는 공백

가정 근거·민감도·경계 계산 및 조건부 승리확률 연결은 prompt 2.6부터
[가정 검토 계약](assumptions.md)으로 구현했다. 새 context의
`model_contract.assumption_review_required`가 일반 판단에 `assumption_review`를
요구한다. 과거 context·판단에는 소급 강제하지 않는다. EPS 배수·DCF 이외의
방법은 미지원 사실과 이유를 기록하며 맞지 않는 방법론을 강제하지 않는다.

형식·참조·산술 검증을 통과했다는 사실은 가정의 설득력이나 투자 판단의
견고함을 검증한 것이 아니다. 2026-09-08 실제 스킬 사용을 검토하면서 다음
한계를 확인했다. 아래 항목은 현재 구현된 검사라고 읽지 않는다.

- **가치평가 가정의 민감도:** 이제 대체 가정과 수익률 경계값을 보존·재계산하지만,
  검사 범위가 충분한지와 출처가 배수를 정당화하는지는 모델의 책임이다. 의도적으로
  좁은 범위만 고르거나 불리한 가정을 누락하는 것까지 산술 검사가 막지는 못한다.
- **승리확률의 품질:** 새 가정 검토는 시나리오별 조건부 승리확률의 가중합과 판단의
  승리확률을 대조한다. 모델이 정한 조건부 확률 자체의 정확성은 검증하지 않는다.
  전체 수익분포의 재현과 확률 보정은 여전히 사후 평가의 대상이다.
- **이익 동인과 매출 비중:** 부문별 이익 자료가 없을 때 매출 비중을 조사 배분의
  대리로 쓸 수 있으나, 그것을 이익 기여율로 승격해서는 안 된다. `researched: true`는
  조사 행위의 기록이며, 필요한 사업별 수익성 자료가 확보됐다는 인증이 아니다.
- **관측할 수 없는 사전 약속:** 신호의 문장·행동을 이어받는 것과 조건의 실제 값을
  관측할 수 있는 것은 다르다. 특히 충당부채 잔액을 분기 전입액으로 대체하거나,
  아직 오지 않은 평가기간을 미발생으로 닫지 않는다. `UNVERIFIABLE`를 허용하는
  현재 계약은 그 신호가 언제까지 관측 불가능해도 되는지와 대체 확인 경로를
  구조화하지 않는다. 확인 불가를 반복해도 매도 규율이 작동한다고 볼 수 없다.
- **출력 의미의 혼합:** 위 Action 절에 적은 대로 `WAIT`에는 가격·사업 판단뿐
  아니라 새 자금 예산이나 정책의 부재도 들어간다. 따라서 `WAIT` 자체를 부정적인
  종목 관점이나 능동적인 저가 매수 대기 계획으로 해석할 수 없다.

이 항목들을 이유로 Python에 매수·매도 판정 규칙을 추가하지 않는다. 개선 대상은
모델이 선택한 가정·반대 근거·관측 한계를 드러내고 재현하는 입력과 출력 계약이다.

```bash
python3.13 -m cio validate decision.json  # 선택: 쓰기 없는 사전검사
python3.13 -m cio record decision.json
```

**packet에는 사용 기한이 있다.** 판단은 context 생성 뒤 12시간 안에 만들어져야
하고(가격의 신선도 기한과 같다 — packet이 그 가격보다 오래 유효할 수 없다),
`record`는 판단을 만든 뒤 12시간 안에만 새로 받는다. 이 기한이 없을 때는 옛
packet을 골라 지금 계약이 요구하는 것(새 경고, 가정 검토, 갱신된 원장)을 피할 수
있었고, 어제의 초안을 오늘 기록하면 그 사이의 가격을 이미 본 판단이 packet의
기준일부터 채점됐다. 저장된 판단 41건은 전부 context 생성 1.6시간 안에
만들어졌다. 기록 시각 검사는 새 기록에만 걸린다 — 저장된 판단의 재검증은 시간이
지나도 같은 답을 낸다.

검증은 context·asset 일치, 시각 순서, 정확한 필드 집합, 유한 숫자, 확률·수익률
산술, 가격 관계, 제안 금액, evidence 참조와 내용 지문을 확인한다. `BLOCKED`
context에서는 숫자 verdict를 기록할 수 없으며 null 수치의 `INSUFFICIENT`만
허용한다. 공식 모델 시도는 `record`를 직접 실행해야 깨진 JSON을 포함한 실패도
quarantine 자산으로 남는다. `assessment_id`는 내용의 지문으로 프로그램이
계산하므로 모델은 생략해도 된다.

형이 틀린 출력(`"verdict": ["WAIT"]`, `"action": "HOLD"`)도 계약 오류다. 값 검사는
객체·문자열이 제자리에 있다고 믿고 내려가므로 형이 틀리면 검사 자체가 성립하지
않는다. 그때는 `schemas/cio-decision.schema.json`의 `type`으로 형이 다른 필드를
전부 찾아 `<필드>: 형이 계약과 다르다 — <기대> 자리에 <실제>`로 알린다. 형 진단은
값 검사가 성립하지 않을 때만 쓰며 평소의 오류 메시지를 대신하지 않는다.

`record`가 검증을 통과한 판단은 `knowledge/assessments/<asset_id>/`에 저장된다.
실패한 출력은 공식 기억에 섞지 않고 `knowledge/quarantine/<asset_id>/`에 오류와
함께 보존해 모델 평가 자료로 사용한다.
